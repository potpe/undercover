# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core. SQLite is the offline/test default; `DATABASE_URL` selects the Supabase session pooler. Both dialects share Core queries in Postgres schema `undercover`, with at most two pooled connections in the backend process to leave session-pooler headroom. APIs cover claims, deterministic payouts, dispatches, evaluations, usage/time ledgers, decisions, sign-off, payment and record-built summaries/scores. Every operation has an `operation_id`, a one-line docstring and no optional request inputs; required nullable fields remain explicit. The backend owns the $1,000 limit, payment guards, run state, handler answer keys and scoring. Its explicit seed path loads plans and complete versioned documents from `context/`; serving/importing the backend does not load the context package or source files. Agent instructions append the documents from the backend documents table. Identical decision/payment replays return the existing records.

Decision records persist `decision`, USD `payout`, `section`, `reason`, required `decided_by`, UTC `decided_at` and `manual_version` from the backend documents table (`2026.2`). Approvals also persist an immutable `calculation` snapshot shaped as `{lines: [{step, amount}], payout}`; the accepted payout must equal that calculation's payout. Current-attempt working calculations are keyed by `failed_attempts + 1`; the latest replaces earlier calculations in that attempt, and only accepted approvals copy one into the decision. Declines/referrals have zero payout and no calculation. Section 14 request/workflow errors are custom 422 refusals; `record_decision` remains a model tool so the graph can return a refusal for correction before an accepted record. Identical decision replays retain the original maker, time and manual version. Judge/evaluation code reads `section` without changing scoring behavior.
- `context/`: independent, read-only MCP service for the seven immutable data-governance files. It prepares the files and numbered document sections once, and returns `{answer, sources}` where each flat source identifies `file`, `system`, `owner` and `reviewed`. Local MCP is at `127.0.0.1:8006/mcp`; the context Lambda handler is `context.server.handler`.
- `agent/main.py`: the hand-written synchronous claim graph retains its claim/document/payout tools, `record_decision` model-tool loop and `interrupt()` sign-off wait. Claim-scoped tool definitions are shared by `agent/direct.py` and `agent/gateway.py`; the model records decisions through a tool, while payment remains graph-only. Direct mode uses the API-key app client and unsigned streamable-HTTP MCP for context tools. Gateway mode uses signed MCP tools with AWS CLI credentials/region. The graph pays small approvals; the backend pays held approvals atomically at sign-off, and resumed graphs finish without another payment call. Screening and claim-model nodes record OpenRouter-reported token usage and `usage.cost`; structured output includes the raw reply so usage is retained. Each invocation records active work, excluding the interval spent waiting for a handler. Claim, screening and improver models cap output at 7,152 tokens to fit the observed provider credit limit.
- `agent/api.py`, `agent/direct.py`, `agent/gateway.py` and `agent/tools.py`: `api.py` owns direct app access and all non-model bookkeeping. `direct.py` and `gateway.py` adapt the same local, claim-scoped tool surface; `tools.py` binds the current claim's identifiers and converts tool errors/refusals. The model cannot choose another claim/policy/customer or a decision maker, and has no payment tool. The backend requires and persists `decided_by`; the agent injects `UnderCover Agent (configuration version N)`, while the screening referral uses `Security check`. `UNDERCOVER_API` (default `http://localhost:8000`), `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_CONTEXT` and `UNDERCOVER_MEMORY_ID` are read at client/claim-graph construction, not import; the memory setting is unused until Phase 4. Short asynchronous MCP operations run on individual worker-thread event loops so the graph and checkpoints remain synchronous and the main thread's event loop is untouched.
- `agent/dispatcher.py`: a model-free synchronous LangGraph graph with no checkpointer. A list node fans out with one `Send` per selected claim, an additive reducer collects results, and `max_concurrency=N` caps workers. `RetryPolicy` retries only `ModelRateLimitError` and `ModelTimeoutError`; exhausted transient work stays in progress, while ordinary errors retain one fresh retry and second-failure handoff. The worker reaches the claim graph through one harness function.
- `agent/checkpoints.py`: each claim keeps its own thread and saver. A process-wide synchronous psycopg `ConnectionPool` uses `min_size=0`, `max_size=4`, `autocommit=True`, `prepare_threshold=0`, `dict_row` and `search_path=undercover`; a separate `PostgresSaver` per claim avoids a shared saver lock. Claims wait for a connection. Tests use isolated synchronous SQLite savers.
- `agent/tracing.py`: Langfuse keeps a stable claim/thread session before and after pauses. Claim config metadata adds `langfuse_tags` with `dispatch-<run_id>` or `evaluation-<run_id>`, so a whole run can be found without merging claim traces.
- `agent/service.py`: a separate FastAPI service on port 8002 starts dispatches/evaluations, works named claims and resumes sign-offs. One non-blocking slot permits only one dispatch/evaluation. The service creates runs through the backend, executes in the background, and marks stale active runs stopped at startup without losing claim checkpoints. `backend/agent_service.py` is the backend's only agent HTTP boundary; the dashboard never calls the service directly.
- `backend/evaluations.py`: seeding stores held-out sources and both handler decision sets in separate backend-only tables. Evaluations create fresh claim ids in both the primary key and JSON record, and copies never enter queue/dispatch selection. Held evaluation approvals finish unpaid, cannot be signed off, and clear saved checkpoints. Backend scoring treats undecided copies as zero-payout referrals and computes decision accuracy, payout accuracy within $1, cost of mistakes, straight-through rate, model cost per claim, active time per claim and whole-run time from its own records.
- `dashboard/`: React, Vite and strict TypeScript. The queue starts N-way dispatches and shows claim progress, record-built summaries and cost/time. The Scoreboard starts whole/tiny evaluations, lists newest first and links handler/agent comparisons to copy pages. Copy pages have no run/sign-off controls. The instructions page shows only the claim agent.
- `e2e/`: Playwright with isolated SQLite business/checkpoint state and a JSON-capturing stand-in agent on port 8003. Automated tests never load `.env`, contact hosted services or call a model.
- `data/`: approved business seed data plus the evaluation sources/labels used only by backend seeding and scoring. The claim agent never reads files or receives handler answers.

The claim graph's first durable node screens the complete policy-plus-claim JSON using Lab 1's fixed instructions and reason-first `Screening` schema. It records raw usage on every structured-output attempt (at most three), refers flagged claims without invoking the claim model, and checkpoints passing results before ordinary work. Default screening uses Luna/`none`; a pinned one-model/default configuration omits reasoning effort. The check is not versioned or editable by the improver. Security seeding appends `CLM-1901`, its policy and customer but not its handler decision; backend label-driven evaluation selection excludes it.

`/api/agent/openapi.json` filters a copy of FastAPI's generated schema to the six app claim-agent operation ids (`get_claim`, `get_policy`, `get_claim_history`, `calculate_payout`, `record_decision` and `pay_claim`), without `servers` or key parameters. Document search and section reads are context MCP tools. Public `pay_claim` checks the current settings limit before looking up a claim; `POST /api/internal/claims/{claim_id}/gateway-hold` accepts a required refusal `reason`, is agent-key-only, and is not exposed in this document or through Gateway. On a Gateway payment refusal, direct bookkeeping records `gateway_refused` and `gateway_refusal_reason` and holds only an approved, unpaid `in_progress` claim for sign-off; the claim bundle exposes those fields. Handler sign-off uses a backend-owned payment helper in the same transaction and makes no agent-service call; graph resumes finish without calling payment again. The API's canonical claim serialization is shared by direct/Gateway `get_claim` and the direct security-check read.

The shared test approval helpers calculate a matching `expense` line under `emergency_medical` for the expected payout plus the plan deductible, then record the exact returned payout and maker. This preserves existing expected payout amounts; backend-only fixtures may write the matching working calculation directly.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `npm run dev` starts backend, agent, context and dashboard; backend and agent receive `.env`, while context has no environment configuration. `uv run -m context` serves MCP at `127.0.0.1:8006/mcp`. `npm run seed` intentionally resets the selected database, including runs, evaluations and checkpoints. `uv run -m agent CLM-1001` works one named claim with no run; bare CLI queue execution is removed.

## Deployment

`npm run build` uses Vite to write `dashboard/dist`, embedding `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from root `.env` or the process environment. Development and production modes can load root `.env`; test mode uses its own environment and never reads root `.env`. With the build present, the backend serves its assets and falls back to `index.html` for non-API dashboard paths; unknown `/api/` requests remain JSON 404 responses. Without the build, development behavior is unchanged.

The Linux x86_64 Python 3.12 app package contains the locked `server` dependency group, `backend/`, `data/` and `dashboard/dist/`; exclude tests, caches, local databases, secrets and packaged `context/` code. `npm run check:server` imports the backend in an isolated server-group environment without changing the project's `.venv`. The Lambda entry point is `backend.main.handler`, using Mangum with `lifespan="off"` so invocation never seeds the database. Ordinary web servers run `backend.main:app`.

The context Lambda is a separate Linux x86_64/Python 3.12 package containing `context/` without tests and the locked `context` dependency group (`mcp`, `mangum`, `pyyaml`). Its entry point is `context.server.handler`, exposed through a Function URL with `AWS_IAM` authorization and no environment variables. `npm run check:context` imports `context.server` in an isolated context-group environment without changing `.venv`. The existing isolated `server` group covers the app and does not install the context group. `langgraph-checkpoint-aws` is a project dependency for the later memory phase; memory runtime behavior is not part of this context-phase build.

Lambda's application environment contains only `DATABASE_URL`, `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`. The publishable key is embedded at build time. AWS supplies `AWS_LAMBDA_FUNCTION_NAME`; when present, backend Postgres uses `NullPool` and `prepare_threshold=None`, opening and closing connections per checkout without retaining them. Set `DATABASE_URL` to Supabase's transaction pooler on port 6543. Laptop and ordinary-server pooling stays at two backend connections; the laptop agent's four-connection checkpoint pool is unchanged.

Only the backend calls the laptop agent service. Agent-started work is unavailable when that service is unreachable; handler reads and atomic sign-off work independently. `UNDERCOVER_API`, `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_CONTEXT` and `UNDERCOVER_MEMORY_ID` are read when clients/claim graphs are constructed, not at module import; `UNDERCOVER_MEMORY_ID` is unused until the later memory phase. The app and packages are described for deployment; this build creates no AWS resources.
